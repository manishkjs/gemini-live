In a real-time voice conversation, standard HTTP metrics like "total request duration" are meaningless because the WebSocket remains open for 10 to 60 minutes. Instead, voice engineering teams track **per-turn voice-to-voice latency** and **per-turn token consumption**.

---

## 1. Anatomy of a sub-second voice turn

True **Voice-to-Voice Latency** is the elapsed time from the **last millisecond of user speech** (`speech_end`) to the **first byte of model audio arriving at the client** (`first_audio_byte`).

<LatencyWaterfall />

| Stage | Typical Duration | What Happens | How to Optimize |
| :--- | :--- | :--- | :--- |
| **1. Network Transport (Client -> Backend -> Vertex)** | `30 to 60 ms` | 20 to 40 ms PCM audio frames traverse WebRTC/WebSocket to the regional endpoint. | Co-locate your Cloud Run / GKE media gateway in `us-central1` alongside the Vertex AI endpoint; use WebRTC (UDP) for the client leg. |
| **2. VAD Silence Duration (`silenceDurationMs`)** | `500 ms` baseline (`350 to 800 ms`) | The server waits after the user stops speaking to confirm the turn is finished. | Use `500 ms` on clean web/headset mics, `600 to 800 ms` on noisy PSTN lines, and lower to `350 to 400 ms` only on clean close-mic transactional bots. |
| **3. Model Time-to-First-Audio-Byte (TTFAB)** | `220 to 350 ms` | `gemini-3.8-live` processes the active context window and synthesizes the first 24 kHz PCM chunk. | Keep active context under 5,000 tokens using [SlidingWindow compression](/gemini-live/optimization/#pillar-1-native-sliding-window-compression-the-15-minute-ceiling-breaker) and modular prompt cards. |

:::tip[Separating VAD wait time from model inference time]
When logging latency in production, always record **Total Turn Latency** (`speech_end → first_audio_byte`) alongside **Model Inference Latency** (`vad_end_of_speech → first_audio_byte`). Otherwise, a deliberate `600ms` `silenceDurationMs` setting will look like a model slowdown on your dashboards.
:::

## 2. Skip the connection wait with pre-warmed sessions

Before the model can answer, your server has to open a WebSocket, send `setup`, and wait for `setupComplete`. If that work starts only when the user speaks, the user hears silence until it finishes.

Pre-warming moves that work earlier. Your backend opens a few sessions ahead of time, finishes setup, and keeps them ready. When a user says the wake word or a call arrives, you hand over a ready session and the model can answer right away.

<PrewarmSequence />

### How it works

1. Before the user speaks: a small pool on your backend opens sessions, sends `setup`, waits for `setupComplete`, and parks them.
2. When the user speaks: your app server takes a parked session from the pool and sends the opening turn.

To see what you gain, log the time from opening the WebSocket to receiving `setupComplete` on a normal cold connection. That is the wait pre-warming removes from the first turn.

### What to load into a parked session

Voice and language are set in `setup` and stay fixed for the session. Instructions and tools can be replaced later with `session.send_context_update()` (`google-genai >= 2.32.0` on `gemini-3.8-live`). That gives you two ways to run a pool:

| | Greeting already loaded | Shared pool |
| :--- | :--- | :--- |
| What `setup` contains | Your real persona, the greeting card, and the greeting card's tools | Voice, language, and your base rules |
| What you send at handover | The opening turn only | `send_context_update()` with the workflow's card and tools, then the opening turn |
| Good fit | Products where every user starts at the same greeting | Gateways that serve several workflows from one pool |

The SDK processes a context update in order with your other inputs, so you can send the update and the opening turn one after the other on the same socket. The SDK also notes that an update "might have a performance impact on model generation". With the greeting already loaded, there is no update at handover, so the first reply does not carry that cost. Measure both options on your own traffic before you choose.

```python
# warm_pool is your own helper. It returns a session that already received setupComplete.

# Option 1: greeting already loaded. Send the opening turn only.
session = await warm_pool.acquire(model="gemini-3.8-live", voice="Puck", language="en-IN")
await session.send_client_content(
    turns=types.Content(
        role="user",
        parts=[types.Part(text="(The device woke up. The user has not spoken yet. Caller name: Alex.)")],
    ),
    turn_complete=True,
)

# Option 2: shared pool. Load this workflow's card and tools, then send the opening turn.
session = await warm_pool.acquire(model="gemini-3.8-live", voice="Puck", language="en-IN")
await session.send_context_update(
    system_instruction=BASE_RULES + ORDER_SUPPORT_CARD + session_state,
    tools=[lookup_order_status, issue_refund],
)
await session.send_client_content(
    turns=types.Content(
        role="user",
        parts=[types.Part(text="(The device woke up. The user has not spoken yet.)")],
    ),
    turn_complete=True,
)
```

In Option 1, one short line of caller facts in the opening turn is enough to greet the user by name. Older turns are trimmed as the call grows, so copy those facts into the session state block of your system instruction at the first card change.

### Keeping the pool healthy

- Keep one pool per model, voice, and language. A context update cannot change the voice or the language.
- Replace parked sessions before they get old. A connection lasts about 10 minutes, and that clock runs while the session waits in the pool. Hand out fresh sessions and close the ones that have waited too long.
- Do not send silence to a parked session. Audio input is billed at about 25 tokens per second, so silence sent to keep a session alive costs money and adds nothing.
- Confirm support before you rely on it. On the Gemini Developer API, check that your API key has `contextUpdate` access. `gemini-live-2.5-flash-native-audio` rejects `contextUpdate` with close code `1007`.
- On wearables, close the link from the device when it is idle. Open the connection from the device to your backend when it is worn or woken, and close it after a few minutes without speech. An open radio link is what drains the battery. The parked sessions live on your backend and do not depend on it.

## 3. Reading `usageMetadata` on every turn

At the end of every model turn (alongside `turnComplete`), the server emits a `usageMetadata` payload breaking down exact token consumption by modality:

```python
async for response in session.receive():
    if response.usage_metadata:
        usage = response.usage_metadata
        print(f"Turn total tokens: {usage.total_token_count}")
        print(f"Prompt tokens:     {usage.prompt_token_count}")
        print(f"Response tokens:   {usage.response_token_count}")

        # Inspect modality breakdown (TEXT vs AUDIO vs VIDEO)
        for detail in usage.prompt_tokens_details or []:
            print(f"  Input {detail.modality}: {detail.token_count} tok")
        for detail in usage.response_tokens_details or []:
            print(f"  Output {detail.modality}: {detail.token_count} tok")
```

### What to alert on in production
1. **Monotonically rising `Input AUDIO` tokens per turn**: Indicates that `contextWindowCompression` is missing or `trigger_tokens` is set too high, causing the [Carried Audio Tax](/gemini-live/pricing/#2-the-multi-turn-carried-audio-tax-quadratic-growth).
2. **High `Input TEXT` tokens on Turn 1 (>1,500 tokens)**: Indicates an oversized static system prompt or bloated MCP/function tool schemas.

## 4. OpenTelemetry per-turn span instrumentation

Emit one OpenTelemetry child span per conversational turn (`gemini_live.turn`) attached to the parent call trace:

```python
import time
from opentelemetry import trace

tracer = trace.get_tracer("gemini.live.voice")

class TurnTelemetryTracker:
    def __init__(self, session_id: str):
        self.session_id = session_id
        self.turn_index = 0
        self.user_speech_ended_at: float | None = None
        self.first_audio_received: bool = False

    def mark_user_speech_end(self):
        self.user_speech_ended_at = time.monotonic()
        self.first_audio_received = False

    def on_first_model_audio_chunk(self):
        if not self.first_audio_received and self.user_speech_ended_at:
            self.first_audio_received = True
            ttfab_ms = (time.monotonic() - self.user_speech_ended_at) * 1000
            return round(ttfab_ms, 1)
        return None

    def record_turn_metrics(self, usage_metadata, ttfab_ms: float | None):
        self.turn_index += 1
        with tracer.start_as_current_span("gemini_live.turn") as span:
            span.set_attribute("session.id", self.session_id)
            span.set_attribute("turn.index", self.turn_index)
            if ttfab_ms is not None:
                span.set_attribute("turn.ttfab_ms", ttfab_ms)
            if usage_metadata:
                span.set_attribute("turn.prompt_tokens", usage_metadata.prompt_token_count or 0)
                span.set_attribute("turn.response_tokens", usage_metadata.response_token_count or 0)
```
