Writing prompts for a full-duplex native audio model is different from prompting a text chatbot. In Gemini Live, `speechConfig`, `tools`, `systemInstruction`, conversation history, and tool responses occupy **fixed relative positions** in the session context on every turn.

Understanding that relative ordering explains both **why certain inputs steer the next spoken reply most strongly** and **how mid-session updates interact with `SlidingWindow` compaction and per-turn token billing**.

---

## 1. How the model prompt is constructed (top to bottom)

Across every turn of a Live session, context operates in three ordered zones from top to bottom:

```text
1. SESSION SETUP (Preserved Across SlidingWindow; Re-Billed Every Turn):
   - Voice configuration                       <- speechConfig (voiceName + languageCode or replicatedVoiceConfig)
   - Active tool schemas                       <- setup.tools (or replaced mid-call via send_context_update)
   - System instruction                        <- setup.systemInstruction (base rules + active phase card + session state)
------------------------------------------------- [SlidingWindow Eviction Boundary]
2. ROLLING CONVERSATION HISTORY (Trimmed at 5,000 -> 3,500 Tokens by SlidingWindow):
   d. Prior caller & model turns               <- Carried audio + transcripts; interrupted model turns are trimmed
                                                   to only the audio the caller actually heard before barging in
3. CURRENT TURN (Highest Recency Weight Right Before Audio Generation):
   e. Latest caller utterance                  <- Current realtimeInput speech + input transcript
   f. Current turn tool calls & FunctionResponse<- *_say fields, <60-token call_state, 1-sentence instruction, vocal_tone
```

### Four architectural consequences of this layout

1. **Why `speechConfig.languageCode` governs Turn 1 and why active tool schemas should stay small**:
   In tests on Vertex AI, `(voiceName, speechConfig.languageCode)` (or your custom `replicatedVoiceConfig` clip) determines the Turn-1 accent baseline: omitting `speechConfig.languageCode` produced an `en-US` accent on Turn 1 even when `systemInstruction` requested Indian English or Hinglish. Always set `speechConfig.languageCode` explicitly (such as `"en-IN"` or `"hi-IN"`) at setup. Likewise, every declared tool schema in `setup.tools` is billed as input text on every turn on Gemini 3.x Live: registering 15 to 20 large tool schemas adds thousands of schema tokens to every turn and dilutes your behavioral instructions. Keeping declared tools scoped to the 1 to 5 schemas needed for the active step prevents schema bloat and lowers per-turn billing.
2. **The newest turn and `FunctionResponse` sit closest to audio generation (Recency Steering)**:
   Because `tools` and `systemInstruction` sit in session setup while turns accumulate below them, twenty turns of audio and transcript history eventually separate your opening instructions from the caller's latest sentence. A `FunctionResponse` returned in the current turn lands right before the model begins generating speech, so it carries strong recency weight for the immediate reply. Use that slot for short, per-turn fields (ready-to-speak `*_say` strings, a `<60-token` `call_state` summary, and a one-line `vocal_tone`), not for whole phase cards: anything returned in a tool payload enters conversation history, is re-billed on later turns, and is evicted when `SlidingWindow` trims old turns.
3. **Update `tools` and `systemInstruction` at stage transitions, not on every turn**:
   Both `tools` and `systemInstruction` stay protected above `SlidingWindow` eviction, and updating either one mid-session via `session.send_context_update()` (or Vertex AI `role="system"`) re-sends the full setup payload. Swap `tools` and `systemInstruction` on stage transitions (`3 to 8 times` per call) rather than on every turn.
4. **Barge-in trims history to what the caller actually heard, and session resumption restores server history**:
   The Live server tracks the playback point where a caller barged in, trimming unplayed model audio out of history and marking the partial transcript as interrupted so the model knows the caller never heard the rest of the cut-off sentence. When reconnecting with `SessionResumptionConfig`, the server restores prior session context directly without re-uploading historical audio.

### Decision matrix: Where each piece of information belongs

| Information Type | Where to Place It | Update Cadence | Billing & Eviction Behavior |
| :--- | :--- | :--- | :--- |
| **Agent persona, vocal tone, speaking pace, and language/gender rules** | `setup.systemInstruction`, plus a one-line `vocal_tone` in every tool result | Set once; repeated in every system-instruction update | Preserved across `SlidingWindow`; billed as text input each turn |
| **Tool schemas (`functionDeclarations`)** | `setup.tools`, then only the current card's tools via `session.send_context_update(tools=[...])` (`google-genai >= 2.32.0`) | On card change (for example, `3 to 8 times` in a multi-step call) | Preserved across `SlidingWindow`; only active schemas billed per turn |
| **Active conversation phase rules (`Phase 2: KYC Verification`)** | Inside `systemInstruction`, replaced in place: `session.send_context_update(system_instruction="...")` (`google-genai >= 2.32.0`), or `clientContent` with `role="system"` (Vertex AI) | On phase transition (for example, `3 to 8 times` in a multi-step call) | Overwrites previous card in place; survives `SlidingWindow` without growing history |
| **Verified caller facts (`FactStore`: name, postal code, ticket ID)** | A `Session state` block inside the same system-instruction update, plus a `<60-token` `call_state` line in each tool result | Updated after key facts are captured | Survives `SlidingWindow` even after early audio turns are evicted |
| **Large reference catalogs or policy docs (`>1,000 tokens`)** | Behind a non-blocking lookup tool (`CallSlots` returning `~25-token` speakable summaries) | Fetched on demand | Zero static prompt tax |

:::note[Why phase cards no longer go in the tail]
A card placed in history (a `role="user"` turn or a full card inside a tool result) is billed again on every later turn: about `635` extra tokens per card in our 3-swap test (`585 -> 1,214 -> 1,853 -> 2,493` prompt tokens). When `SlidingWindow` compression trims history at `5,000` tokens, the card disappears and the model falls back to the opening greeting (6 of 7 runs). A system-instruction update overwrites the old card, survives compression, and grew only `~65` tokens per swap (`585 -> 647 -> 713 -> 783`), saving thousands of billed tokens across the call. Details: [Pillar 2: Dynamic prompt cards](/gemini-live/optimization/prompt-cards/).
:::

## 2. How to structure a production `systemInstruction`

A reliable voice `systemInstruction` stays under **500 tokens** and is organized into four distinct blocks:

```text
1. PERSONA & ACOUSTIC DELIVERY
You are Maya, a senior technical support specialist at Cymbal Fiber.
Speak in a warm, calm, conversational tone. Keep every response to 1 or 2 short sentences (15 to 35 words), then pause so the caller can reply.
Read confirmation numbers, postal codes, and phone numbers one digit at a time ("four, two, nine").

2. LANGUAGE PINNING & ACOUSTIC FILTERING
Speak exclusively in English. Every word you output must remain in English regardless of background noise, coughs, or caller accent.
The caller may be in a noisy environment. Ignore background conversations, side chatter, and non-directed sounds.

3. POSITIVE TOOL & TURN RULES
When you invoke a tool, first speak a brief natural acknowledgment ("Let me check your line status right now."), then emit the tool call. When the result arrives, speak its spoken fields right away.

4. OPENING PHASE (STEP 1: GREETING & INTENT)
a) Greet the caller briefly and ask how you can help today.
b) Listen to their complete answer.
c) Call lookup_customer_account with their stated issue and wait for the tool response before advancing.
```

### Why each block is written this way

#### A. Positive behavioral framing beats negative prohibitions
Under real-time audio streaming, negative instructions (*"Do NOT narrate tool calls"*, *"Do NOT ask two questions at once"*, *"Never repeat yourself"*) frequently backfire because they prime token attention on the forbidden action. Rewrite prohibitions into positive actions that tell the model what to do next:

| Fragile Negative Prompt | Production Positive Rewrite |
| :--- | :--- |
| *"Do NOT announce when you are calling a function or read out parameter names."* | *"Before invoking a tool, speak one natural sentence ('Let me check that for you.'), emit the tool call, and immediately stop speaking."* |
| *"Never ask multiple questions in the same turn or give long paragraphs."* | *"Ask exactly one question per turn, keep your reply under 30 words, and wait for the caller to answer."* |
| *"Do not switch languages if you hear background noise."* | *"Speak unmistakably in the call language on every turn, even if background voices or accents sound like another language."* |

#### B. Pair `speechConfig.languageCode` with short turns (`<60 words`) and in-place phonetic spellings
For regional accents and multilingual voice agents, pair `speechConfig.languageCode` (for example `"en-IN"`) with positive phrasing (`"RESPOND UNMISTAKABLY IN HINGLISH with a natural Indian accent on every word"`). Keep every spoken reply under 2 to 3 short sentences (under 60 words total) so the voice does not accelerate into a rushed read-aloud cadence on long explanations. When a brand name or model code needs a specific pronunciation, write the phonetic spelling directly in place in Latin script (`"B-E six Sporteq"`): in field testing, native audio models often read both sides of an inline `"Pronounce X as Y"` table aloud or stumble over mixed-script mid-word hyphenation (`"BE 6 को 'बी-ई सिक्स' बोलें"`).

#### C. Prescriptive `a -> b -> c` sequences prevent turn-boundary guessing
When a phase requires asking a question and calling a tool, spell out the exact turn boundary using lettered steps (`a, b, c`) so the model does not call the tool before the caller answers.

#### D. Single source of truth (no duplicate instructions)
If a phase directive or follow-up question is delivered dynamically (in the current card or a tool response), **remove that instruction from the base rules**. Keeping the same instruction in both places causes the model to deliver the prompt twice.

## 3. Acoustic traps that break native audio sessions

Native speech-to-speech models process text instructions directly in the acoustic domain. Avoid these failure modes:

1. **Never use square brackets (`[PAUSE]`, `[SYSTEM_NOTE]`, `[EMPATHETIC]`)**:
   Native audio models frequently treat bracketed tags as literal words to read aloud (*"bracket system note bracket"*) or shift into exaggerated theatrical prosody. Always use plain conversational prose (`"System update for agent: ..."`).
2. **Never instruct the model to `"stay silent"`, `"wait silently"`, or `"produce no audio"`**:
   When a Gemini Live model generates zero audio tokens for an entire turn, the backend suppresses `inputAudioTranscription` events for that turn as well, blinding your server-side transcript logger and state machine. The same rule causes two more failures in production: long dead air (the model declines to answer and the server sends no signal, so the caller waits) and placeholder leaks (the model writes `<no speech>` into its output transcript and can say "no speech" aloud). If the client needs silence while background work runs, gate audio or use `FunctionResponseScheduling.SILENT` on the tool response. If the caller only says "okay" or "haan", handle it in the client (see [Short backchannels after a barge-in](/gemini-live/gemini-live-configuration/#short-backchannels-after-a-barge-in)) or tell the model to ask one short follow-up question.
3. **Never send `clientContent` while the model is actively speaking**:
   A `BidiGenerateContentClientContent` message with `turn_complete=True` sent during active model generation is a new user turn and cuts off the model's in-flight speech. A `turn_complete=False` update usually lets the reply finish (14 of 16 measured runs on Vertex AI `gemini-3.8-live` and `gemini-live-2.5-flash-native-audio`), but it only applies from the next turn. Send updates after `turnComplete`, or inside a blocking tool handler right before you return the `FunctionResponse`.
4. **Never wrap spoken lines in XML tags (`<verbatim>`, `<say>`, `<script>`)**:
   Asking the model to read back text inside tags such as `<verbatim>...</verbatim>` makes `gemini-3.8-live` dump the whole line into the output transcript in one or two frames and send `generationComplete` after less than a second of audio (or none). In one test this cut off 7 of 25 turns (28%). Put the exact line in a plain `*_say` field of a tool result and tell the model to say it exactly as given.
5. **Ban non-lexical fillers (`"Hmm..."`, `"Umm..."`, `"Ahh..."`)**:
   The model renders these as breathy sounds, and on female voices they can drop the pitch into a deep chest register that does not match the rest of the call. Ask for short real words instead: "Sure", "Right", "One moment", or "जी" on Hindi calls.
6. **Do not use greedy decoding (`temperature: 0` or `topK: 1`) or low-temperature sampling (`temperature <= 0.3`) to get consistent wording**:
   When a tool result contains a long formal string (such as a person's name plus a corporate title), the audio head can finish speaking the natural question in ~3 seconds while the text stream (`outputTranscription`) keeps flushing the remaining title words over 4 to 5 seconds of near-silence. Inside that silent window, the model fails to emit its end-of-turn token (so `turnComplete` never arrives) and can lock into a ~20-second nasal hum near the voice's fundamental pitch (~187 to 200 Hz in one measured cloned-voice session) until the server's turn-length cap cuts it off. Leave `temperature` unset (default `1.0`) or between `0.7` and `1.0`, leave `topK` and `topP` unset, and keep spoken `*_say` strings concise. See [Sampling for audio output](/gemini-live/gemini-live-configuration/#sampling-for-audio-output).
7. **Do not paste inline pronunciation tables (`"Pronounce X as Y"`) into `systemInstruction`**:
   Write phonetic spellings for brand acronyms directly in place in Latin script (`"B-E six Sporteq"`; see [Short turns and in-place phonetic spellings](#b-pair-speechconfiglanguagecode-with-short-turns-60-words-and-in-place-phonetic-spellings)).

## 4. Steering mid-session: system-instruction cards & short tool results

To steer the model across a multi-step call without growing history on every phase change:

1. **Replace the card in `systemInstruction`, do not stack it in history.** On each phase change, send one system-instruction update that holds `base rules + current card + session state`: `await session.send_context_update(system_instruction=..., tools=...)` (`google-genai >= 2.32.0`), or `clientContent` with `role="system"` and `turn_complete=False` on Vertex AI models that do not support `contextUpdate` (such as Gemini 2.5 native audio). On `gemini-3.8-live`, swap the card's tools in the same `send_context_update` call.
2. **Send the update inside the blocking tool handler**, right before you return the `FunctionResponse`. The model is paused waiting for the result, so the update never races its speech.
3. **Return a short tool result that points at the card.** Keep `call_state` (`<60` tokens of confirmed facts), a one-sentence `instruction`, and a one-line `prompt_card` pointer such as *"Prompt card 4 of 8 (Return Flight Selection) is now in your system instruction. Follow it."* See [Tools -> What to put in a FunctionResponse](/gemini-live/tools/#8-what-to-put-in-a-functionresponse).
4. **Repeat persona grammar rules inside multilingual phase cards**: In gendered languages (such as Hindi, Spanish, or French), include a one-line persona grammar header in each card so the model never drifts from its assigned speaker gender.

### Opening the call: a language-neutral Turn-0 stub

Many clients open the call by sending a short text-only user turn on Turn 0 so the model speaks first. Because that opening trigger has zero caller audio in history, the setup voice profile (`speechConfig`) is the only acoustic reference for the greeting: always set `speechConfig.languageCode` explicitly (for example, `"en-IN"`) in `setup` so the opening greeting does not default to the `en-US` studio voice. Do not make that trigger turn a greeting in any language. On a multilingual agent, a stub like `"नमस्ते!"` reads as the caller choosing Hindi: the model skips its introduction and calls the language tool on Turn 0. Send a neutral stage note (`GREETING_STUB` below), and pair it with an opening rule in the first system instruction:

```python
GREETING_STUB = "(The call has connected. The caller has not spoken yet.)"

START = (
    "START\n"
    f'The message "{GREETING_STUB}" only means the call has connected. It is not the caller '
    "speaking and not a language choice. Do not call a tool for it. Say only: "
    '"Hello, I am Asha from Cymbal Travel. Which language would you like to talk in?"'
)

IN_CALL = (
    "IN CALL\n"
    "The greeting and the language choice are done. Never greet again or ask for the language "
    "again. Older turns may be missing: the prompt card and session state below are the truth."
)
```

Build the setup instruction with `START`. From the first card change onward, build every system-instruction update with `IN_CALL` in its place. After a `SlidingWindow` trim or a session resumption, the opening turns may be gone, and `IN_CALL` stops the model from greeting the caller a second time.
